## The account rule (matrix row 10), examined

**Which identity the rule applies to.** The rule applies to every Windows account that **owns a process reading the publication**: the Arena admin window, admin console and event service. F:'s `Get-LabArenaIdentity` already finds these by process owner SID; it should pass all of them as `-ArenaAccount`.
- The account is what matters, not whether a given process is elevated.
- A UAC-filtered administrator token cannot use its Administrators membership while unelevated. But the same account can elevate at will.
- So a filtered admin token is not a boundary.

**Why the rule is necessary.** No ACL protects the ledger from a member of Administrators. Such a member can take ownership and rewrite the ACL. Backup Operators read any file through backup privilege, so the same applies to them. Keeping Arena out of the private ledger, state, logs and key therefore requires Arena to run as a standard account.

**Corrections made in 0.3.0.** The 0.2.0 check was too weak in four ways:
1. **It failed open.** When `Get-LocalGroupMember` threw, it reported "not checked" with `ok: true`. On this development machine it does throw (error 1789, an unresolvable member).
   - Now the script falls back to the WinNT provider, as F: does.
   - If membership still cannot be read, that is a finding.
2. **It checked direct membership only.** Now nested local groups are expanded. A group that cannot be expanded is a finding.
3. **It ignored Backup Operators.** Now checked.
4. **It accepted one Arena account.** Now it accepts several.

Also added: the Gateway account being privileged is a warning here, and a blocking check in `plan`, `install` and `verify`. The separation is unchanged; none of these corrections weakens it.

**F: impact.** `Get-LabGatewayAccountVerdict` checks direct membership only. Either adopt transitive membership including Backup Operators, or rely on the Gateway script's JSON, which is authoritative.
